🧭 3. Sensors, IMU, Compass & Battery Peripherals

The IMU and magnetometer are detected by the firmware at boot and their drivers chosen at run time (i2cProbeSelect), so swapping either one needs no change here — plug it in and reboot the board. Everything else on this page the firmware cannot discover for itself: the barometer is a compile-time choice (its publishers exist only if it was built in and the chip answered at boot), the battery monitor likewise, and the ADC divider resistors and sonar pins are properties of your wiring — read them wrong and you read the battery wrong.

🤖 I2C Bus Probe

Runs the same scan the firmware runs at every boot (WHO_AM_I identification, firmware/common/lib/i2c_probe) and shows what answered. This is a read-out, not a setting: whatever is on the bus is what the robot firmware will drive.

LiDAR 2D Laser Scanner & 3D Depth Camera

Primary distance perception sensors for 2D SLAM, obstacle avoidance, and Nav2 costmaps. Configured sensors synchronize with Bringup launchers.

For live radar visualization and UDP bridge setup, use the LiDAR / Scan ➔ tab.
Generates 3D pointclouds and synthetic 2D laser scans.

Inertial Measurement Unit (IMU) & Magnetometer

The bus overrules this. The firmware scans I2C during startup, prints what it found over serial ([i2c] IMU: the bus says MPU6050 at 0x68 …) and enables that driver even when the selection above says otherwise — so a wrong choice costs a log line, not a boot loop. These values are what the board falls back to when nothing answers. Swapping an IMU needs no rebuild: every driver is compiled into the image. Use Fake Mode below to force the simulated sensors on a board with nothing wired.

ICM20948 is one chip with two entries. Its AK09916 magnetometer sits on the IMU's internal auxiliary bus and never answers the main bus on its own, so set both selects to ICM20948 to publish /imu/mag.

🔌 Serial Debug Monitor Not connected

Opens a board's serial port from this browser and shows its raw output — the equivalent of pio device monitor for the machine you are sitting at. Handy for reading a boot log or driving the test_sensors / i2c_detect diagnostic firmwares.

Monitoring only — this never flashes. Firmware is written natively on the robot computer by esptool / picotool, which is the only path that can stop micro_ros_agent, confirm the port was released and restart it afterwards. A browser tab cannot, and a half-written flash bricks the board.

🗺️ 9. Visualize & SLAM Mapping / Nav2 Navigation (RViz via browser)

      
Most robot computers are headless -- RViz has nowhere to open a window
        on. This runs RViz against a virtual display and serves it over noVNC, the same idea
        as the kasmvnc service in the cockpit's docker/docker-compose.yaml,
        but native (no Docker) to match how the rest of the cockpit installs things. Works whether
        you're viewing from the robot computer itself or a separate laptop on the network.

      
Heavier than the rest of the cockpit -- RViz is a full Qt/OpenGL app,
        and on a small SBC (limited CPU, 4GB RAM class) running it headlessly through Xvfb adds
        real CPU/memory load on top of Bringup/Nav2. On constrained hardware, prefer the plain
        LiDAR / Scan tab's /scan canvas viewer (much cheaper) and only reach for this
        when you actually need the full map/costmap/TF view.

      

        
        
        
      

      
The Teleop view is the one to use with a bare module running
        USE_FAKE_WHEEL firmware: the fixed frame is odom, so the robot
        is seen driving away from where it started, with odometry arrows tracing the path it
        thinks it took. Bare rviz2 opens with nothing configured and will look
        empty while you drive.

    🕹️ 8. Manual Teleop & Velocity Driving — virtual gamepad no hardware needed
    
      
    Drive the robot from this page -- no physical joystick, and no
        terminal for teleop_twist_keyboard. Drag the stick (or use the arrow
        keys / WASD while it has focus) and the cockpit publishes /cmd_vel at
        20 Hz. Pair it with the Teleop RViz view to watch the robot move,
        which on a bare module running USE_FAKE_WHEEL firmware is the whole
        robot: cmd_vel drives the simulated wheels and the odometry comes back.
    
      
    Deadman built in -- the robot is commanded to zero if this
        page stops sending for half a second, so closing the tab or losing Wi-Fi stops
        the robot instead of leaving it driving on the last command.

    📡 6. Standalone Laser Driver & Radar Viewer
    
        Live Sensor Stream
      
    
      
    Directly run and verify the 2D LiDAR driver independently of the micro-ROS autonomy stack. Configured model synchronizes with Sensors tab.
        It needs no micro-ROS agent -- the LiDAR talks to the robot computer directly (USB
        serial or its own WiFi-UDP relay), not through the MCU/agent link.
    
      
    
        
      
    

      
    
        
      
    

      
    
        
        
      
    
      
      
    Stored as /dev/serial/by-path/… (the physical USB port),
        which survives reboot and replug — unlike /dev/ttyUSBn, and
        unlike by-id, which many generic CP2102/CH340 lidar bridges can't populate.
        Most lidars share a generic UART chip, so pick by physical port; re-run
        detect after replugging to see which entry moved.
    
      
    

      
    
        
    
          
          
        
    
        
    
          
    The MCU relays raw LiDAR UART bytes as UDP datagrams to this port
            (its LIDAR_PORT/AGENT_IP setting in config-engine must
            point at this robot computer). The cockpit bridges them into a local persistent serial
            device with socat, then points the driver at that device -- there's no
            other consumer for this feed today.
    
          
          
        
    
        
    
          
          
        
    
      
    

      
      
    
    

    
    
      
    Live /scan viewer
    
      
    Plots sensor_msgs/LaserScan straight from the ROS graph, so it
        needs the laser driver (or Bringup) publishing already. Cheap enough for a small SBC --
        for the full map / costmap / TF view use the RViz-in-browser card on the
        Operations tab.
    
      
    
        
        
        Which topic to plot. Change it for a robot publishing
          under a namespace (/robot1/scan) or a second laser on a topic of
          its own (/scan_raw).

        own docker/Dockerfile builds everything (including sensor drivers) inside
        the image; the console drives it from its own compose stack at
        tools/console/docker/. Useful on unsupported OS versions, or when
        you'd rather not touch the host. Native builds directly on this machine instead.
    
    
    

    
    
      
    
        
    1. Base install
    
        
    Clones linorobot2 (branch = detected $ROS_DISTRO) into the
          workspace, skips the Gazebo package, then rosdep install + colcon build.
          No setup script is invoked.
    
        
      
    

      
    
        
    2. Laser sensor (optional)
    
        
    
          
          
          
        
    
      
    

      
    
        
    3. Depth camera (optional)
    
        
    
          
          
          
        
    
      
    
    
    

    
    
      
    
        
    1. Build image
    
        
    
          
          
          
        
    
        
    
          
          
          
          
        
    
        
    Writes tools/console/docker/.env +
          devices.generated.yaml (the base serial + lidar device mappings) into the
          console's own compose dir -- the repo's docker/ is never written --
          then clones linorobot2 (if needed) and runs
          docker compose --env-file .env -f docker-compose.yaml -f devices.generated.yaml build.
          Sensor drivers install inside the image via linorobot2's own install.bash
          (the documented Docker build path, not run on this host).
    
        
      
    

      
    
        
    2. Host udev rules
    
        
    The image already contains the sensor drivers -- this only creates the
          persistent /dev/<sensor> symlink on the host, using the cockpit's own
          native udev-rule commands (same as the native Laser/Depth sensor install cards above),
          not install.bash.
    
        
      
    

      
    
        
    3. Run a service
    
        
    
          
        
    
        
    Runs in the foreground through the same console pane as everything else
          in the cockpit -- Stop sends the container(s) a normal compose stop signal.
          Start kasmvnc alongside bringup/slam/etc. (in a
          second cockpit tab, since each occupies the one exec slot) for GUI output from any of
          them.

        🐳
        
    
          
    Linux Rootless Container Guide
    
          
    Prevent root file ownership on bind-mounted directories
    
        
    
      
    
      
    
    

    
    
      
    💡 Why Rootless Docker on Linux?
    
      
    
        When standard (rootful) Docker executes container builds with volume mounts (-v "$(pwd):/workspace"), all generated files (such as .env, devices.generated.yaml, and build artifacts) are written as root:root. This causes local Git commit errors and permission denies during local development.
        Rootless Docker and Podman run completely inside your user namespace, guaranteeing all files stay owned by your normal user account.
      
    
    
    

    
    
      
    
        ⚡ 1-Click Setup: Ubuntu / Debian / Raspberry Pi OS
        
      
    
      
    # 1. Install prerequisites
sudo apt-get update && sudo apt-get install -y uidmap dbus-user-session slirp4netns
# 2. Run official rootless installer (non-root)
dockerd-rootless-setuptool.sh install
# 3. Enable user systemd service and persistent lingering
systemctl --user enable --now docker.service
loginctl enable-linger $USER
# 4. Point DOCKER_HOST to your user socket
export DOCKER_HOST="unix://${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/docker.sock"
grep -q "DOCKER_HOST" ~/.bashrc || echo 'export DOCKER_HOST="unix://${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/docker.sock"' >> ~/.bashrc
    
    
    

    
    
      
    
        🦭 Alternative: Podman (Rootless by Default — No Daemon!)
        
      
    
      
    sudo apt-get install -y podman  # Fedora: sudo dnf install -y podman
# Podman works immediately with zero daemon configuration:
podman run --rm hello-world
    
    
    

    
    
      🖥️ Windows & macOS Note
      
    
        On Windows (WSL2 / Docker Desktop) and macOS (Docker Desktop / Colima), volume mount permissions are already automatically mapped to the host user by the hypervisor layer. No rootless daemon configuration is required.
